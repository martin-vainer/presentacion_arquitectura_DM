01 / Visión

Objetivos

Un backend que interpreta preguntas de negocio y ejecuta consultas confiables sobre modelos semánticos existentes.

Problema

Obtener métricas específicas requiere analistas, consultas ad-hoc o dashboards rígidos.

Propuesta

Un backend agéntico en Python que entiende lenguaje natural y consulta modelos semánticos existentes en Fabric.

Por qué ahora

El ecosistema de agentes maduró en 2025-2026: Agent Framework 1.0, MCP e interoperabilidad entre agentes.

Principio rector

El LLM interpreta; los catálogos validan; Fabric ejecuta. El sistema no inventa métricas, filtros ni consultas.

Consultas esperadas

¿Cuántos clientes activos tenemos este mes?
¿Cuál es el ratio de mora de la cartera X en los últimos 3 meses?
Dame el saldo total del segmento Y al último período cerrado.

05 / Decisión tecnológica

Por qué Microsoft Agent Framework

Para este caso, la integración empresarial pesa más que la flexibilidad experimental.

Recomendado

Microsoft Agent Framework 1.0

  • Sucesor oficial de Semantic Kernel + AutoGen.
  • Integración natural con Azure OpenAI, Entra ID y Monitor.
  • MCP y A2A en el modelo de integración.
  • Workflow graphs para control explícito.
Alternativa técnica

LangGraph

Excelente para grafos de agentes, pero fuera del ecosistema Microsoft y con otro modelo de soporte.

Legado directo

Semantic Kernel / AutoGen standalone

Referencias relevantes, pero absorbidas en el camino recomendado de Agent Framework para proyectos nuevos.

Liviano

Pydantic AI

Tipado y simple, pero con menor madurez empresarial para un contexto bancario Microsoft-first.

La decisión final depende del lineamiento corporativo vigente sobre frameworks de agentes.

08 / Dominio

El corazón del sistema: los catálogos

El LLM elige entre candidatos validados. Nunca crea una métrica nueva por su cuenta.

Capa 1

Fuente de verdad

Catálogo YAML/JSON versionado en Git, con schema Pydantic estricto y ownership funcional.

Capa 2

Asistente de búsqueda

RAG con embeddings en Azure AI Search, generado automáticamente desde la capa estructurada.

Linaje técnico

El linaje desde ETLs complementa la trazabilidad; no reemplaza la definición de negocio.

Riesgo principal

El mantenimiento del catálogo es un problema de gobierno, no solamente técnico.

metric.yamlschema validado
metric_id: irregularidad_tarjetas
business_name: Irregularidad de tarjetas
aliases:

10 / Caso guiado

Ejemplo: consulta de irregularidad en tarjetas

Caso concreto de punta a punta para mostrar cómo se combina interpretación del LLM con verdad técnica del catálogo.

“¿Cuántas tarjetas en irregularidad tenemos este mes en el segmento premium?”
1

Recepción e interpretación inicial

El agente intérprete identifica entidades (“tarjetas”, “irregularidad”, “este mes”, “segmento premium”) y arma un intent tentativo.

Input / Output

Input: consulta en lenguaje natural Output: intent_tentativo = consulta de métrica sobre cartera de tarjetas con filtro de irregularidad y segmento.

2

Búsqueda semántica en capa 2

Se embebe “tarjetas en irregularidad” y se consulta el vector store para recuperar candidatos por similitud.

Output de ejemplo

Candidatos: - cantidad_tarjetas_irregulares (score: 0.91) - ratio_irregularidad_tarjetas (score: 0.84) - cantidad_tarjetas_activas (score: 0.62)

3

Validación contra capa 1

Se toman los IDs candidatos y se trae su definición completa del catálogo estructurado.

YAML resumido

metric_id: cantidad_tarjetas_irregulares business_name: "Cantidad de Tarjetas en Irregularidad" aliases: - "tarjetas irregulares" - "tarjetas en situacion 3 o mas" - "tarjetas con mora" definition: "Cantidad de tarjetas de crédito cuya situación en el modelo semántico es >= 3, calculada al cierre del período." domain: "riesgo_crediticio" semantic_model: "Modelo_Riesgo_Tarjetas" dax_template: "CALCULATE([Cantidad Tarjetas], Tarjetas[situacion] >= 3, {filtros_adicionales})" supported_filters: - segmento_comercial: [premium, standard, basico] - region: dynamic - situacion: [1, 2, 3, 4, 5]

4

Resolución semántica de “irregularidad”

El agente traduce el concepto de negocio a una regla técnica usando el léxico semántico.

Output de ejemplo

# lexicon/business_concepts.yaml irregularidad_tarjetas: canonical_name: "situacion_irregular" mapping_rule: field: "situacion" operator: ">=" value: 3 synonyms: - "irregularidad" - "situacion 3 o mas" - "en mora" - "con atraso significativo"

5

Validación del plan de consulta

Se compone el DAX final desde template parametrizado y se valida que todos los filtros estén permitidos.

DAX final construido

CALCULATE( [Cantidad Tarjetas], Tarjetas[situacion] >= 3, Tarjetas[segmento_comercial] = "premium", DATESINPERIOD( Calendario[Fecha], MAX(Calendario[Fecha]), -1, MONTH ) )

El DAX no fue inventado: surge de combinar el template de la métrica, el mapeo de “irregularidad” del léxico, el filtro de segmento y la resolución temporal de “este mes”.
6

Ejecución y respuesta enriquecida

El adaptador de Fabric ejecuta vía Execute Queries REST API y devuelve valor + contexto de trazabilidad.

Respuesta JSON de ejemplo

{ "metric": "cantidad_tarjetas_irregulares", "value": 12847, "unit": "count", "period": "2026-04", "filters_applied": { "segmento_comercial": "premium", "situacion": ">= 3" }, "related_metrics": [ "ratio_irregularidad_tarjetas", "cantidad_tarjetas_activas" ], "trace_id": "req_a7f3k2..." }

“El LLM interpretó lenguaje natural, el catálogo aportó la verdad técnica, la ejecución fue determinística. Cero alucinación.”
11 / Puente semántico

Léxico semántico: el puente entre negocio y modelo

Permite traducir conceptos de negocio imprecisos a reglas técnicas exactas aplicables sobre el modelo semántico.

Tercera pieza del catálogo estructurado

Además de métricas y variables, el léxico semántico codifica cómo términos de negocio se convierten en reglas técnicas estables para consulta.

Concepto de negocioCampo en modeloRegla técnica
irregularidad tarjetassituacion>= 3
cartera sanasituacion= 1
cliente activoultima_transaccion>= HOY - 30 días
mora tempranadias_atrasoentre 1 y 30
mora avanzadadias_atraso> 90
El léxico semántico es curado manualmente por el owner del catálogo. Codifica decisiones de negocio que no están en el código ETL ni en los metadatos técnicos.

Este componente permite que usuarios distintos consulten lo mismo usando su propia jerga, y el agente siempre lo resuelva al mismo DAX subyacente.

12 / Integración

Integración con Fabric / Power BI

La ejecución se apoya en modelos semánticos existentes y evita DAX libre generado sin control.

Camino propuesto

  • Power BI Execute Queries REST API para ejecutar DAX.
  • Autenticación con Service Principal en Entra ID.
  • DAX generado desde templates parametrizados.
  • Resultado validado antes de construir la respuesta final.

Decisiones y límites

  • No usar Semantic Link / SemPy para backend externo: está soportado dentro de Fabric.
  • XMLA endpoint como posibilidad futura para casos complejos.
  • Validar restricciones de Service Principal, RLS, SSO y políticas tenant.
13 / Interoperabilidad

MCP: qué es y cómo se integra

MCP expone herramientas a clientes de IA. En este diseño es transporte, no dominio.

Aclaración conceptual

  • MCP es un protocolo estándar abierto para conectar clientes de IA con servidores que exponen herramientas.
  • El servidor MCP es una fachada delgada sobre el backend.
  • La lógica vive en el backend: catálogos, validación, orquestación y ejecución.
  • Se agrega después del MVP.
